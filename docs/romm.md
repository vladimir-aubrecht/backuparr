# RomM API backup and recovery

This driver targets **RomM 5.4.0**. Other versions are rejected until their API
contract has been verified. It is a recoverable API export, not a database dump.
No RomM volumes or Docker socket are mounted into Backuparr.

In RomM, create an **administrator client token** with `me.read`, `roms.read`,
`roms.write`, `roms.user.read`, `roms.user.write`, `platforms.read`,
`platforms.write`, `collections.read`, `collections.write`, `assets.read`, and
`assets.write`, and `me.write`. Paste the token into Backuparr's API key field. Tokens belong to
one account: an administrator token cannot read or restore another account's
private saves, notes, collections or play status. Configure/run a separate export
with each account's token to cover its data (this driver currently requires an
administrator account). Test connection checks the read endpoints; RomM does not
expose the current token's effective write scopes for preflight introspection.

The archive includes:

- Every visible ROM plus the owner's hidden ROMs, without grouping duplicates:
  content/path identity for migration, editable title/sort title/summary, manual
  metadata, and provider IDs/raw metadata accepted by RomM's update endpoint.
- The token owner's backlog, playing/hidden/main-sibling flags, rating,
  difficulty, completion and completion status; private/public notes and tags.
- The owner's normal/favorite collections and membership, smart collections
  and their filter definitions. Platform and collection references are remapped.
- The owner's save files, emulator states, attached thumbnails and gallery
  screenshots, including emulator, visibility, favorite flags and labels.
- Streaming emulator memory cards and their complete image history (oldest first
  on recovery). The latest archived version becomes the recovered card's current
  content. Recovery creates a new card; repeated recovery creates additional cards.
- The connected account's email, RetroAchievements username and avatar. Platforms'
  custom names and descriptions are also restored.
  An empty RetroAchievements username or absent avatar cannot clear a target value
  through RomM's API; existing target values are retained in those two cases.
- ROM/collection covers and ROM manuals. These are downloaded from RomM's
  same-origin `/assets/romm/resources/` paths advertised by the API and uploaded
  back through the API. That resource path must be reachable through any reverse
  proxy. Redirects to a login service are refused, and the backup fails instead
  of accepting a login page as file data.
- Writable scan/artwork priority settings, conversions, platform bindings/version
  bindings and configured exclusions. Every binary has a SHA-256 checksum.
  Provider cache paths embedding old database IDs are removed; cached provider
  images apart from the explicitly archived covers/manuals are regenerated by RomM.

**Not included:** ROM/BIOS binaries, full SQL database, password/token material,
environment configuration, full `config.yml`, permission groups, music/playlists,
patches, generated virtual collections, device/sync history, RetroAchievements,
play-session history, browser preferences and pinned media.
Metadata without a write API (for example computed technical/file fields) is
not replayed. Exact last-played timestamps cannot be set through RomM's property
API; uploading a save/state sets last-played to the time of recovery. Save/state
IDs and creation/update times are regenerated. Newly uploaded slotted save versions
are restored as ordinary saves so RomM's slot retention cannot remove versions during recovery;
their bytes and emulator are preserved, but slot/sync attribution is not.
Updating an existing same-name save retains its existing slot attribution.

## Restore

1. Install **the same RomM version**, recreate the original username, restore the
   ROM/BIOS library separately, and scan it. Retain the relative library paths
   when hashes are unavailable. Ensure RomM can write its own `config.yml`.
2. Pause users, scans and automatic metadata refreshes. Back up the current target
   before recovery. The API has no multi-request transaction or rollback.
3. Download the archive from Backuparr History. Run a preview inside Backuparr:

   ```sh
   python -m apps.romm_restore /path/to/romm-backup.zip
   ```

   The command reads the existing encrypted RomM settings. For a separate target,
   use `--url http://romm:8080 --api-key-file /run/secrets/romm-token`. Do not put
   a token directly in shell command arguments.
4. After the preview succeeds, repeat with `--apply`. It validates the manifest,
   all checksums, account ownership, and every ROM/platform/collection mapping
   before writing. Ambiguous/missing ROMs fail before upload; display titles and
   old database IDs are never used as migration matches. Public collections owned
   by another user and referenced by smart collections must exist on the target.

Restore overwrites the backed-up metadata/status, matching asset filenames,
collection membership and listed settings. It creates missing collections and
notes, and leaves unrelated target objects in place. A repeated restore can
reuse matching filenames/collection names. API errors stop the process; completed
requests remain applied. Provider ID changes may contact the configured metadata
providers before the saved raw metadata is reapplied. Cover/manual uploads become
custom (locked) resources on RomM. Verify recovered content before resuming users.

The web Restore button is disabled because this recovery requires explicit
preflight and recreation/scanning of the library. The CLI performs the actual
restore; this is not an export that requires an unwritten importer.
